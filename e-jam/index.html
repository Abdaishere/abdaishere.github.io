01 · The problem

Proving a switch is sound took an afternoon and a person

A network switch is the box every packet in an office passes through, and a new one has to prove it can carry full traffic without dropping or delaying anything. The proof is a standard set of measurements (throughput, latency, frame loss) at several frame sizes, each repeated many times. Done by hand, one full pass took an engineer more than two hours, and the hand was the slow part.

Two RFCs define what those measurements mean. RFC 2544 finds throughput by binary search on the send rate: every trial runs at least 30 seconds and the final one at least 60, and a trial passes only if nothing is dropped. Latency comes from a single tagged frame dropped into a 60-second stream, timestamped on the way in and the way out, over at least 20 trials. Frame loss is at least 10 trials per frame size, starting at the full rate and stepping down. RFC 2889 covers the switching cases on top of that, and RFC 1242 and RFC 2285 supply the vocabulary both of them use.

None of that is difficult. All of it is long, repetitive and exactly the kind of work a person does slightly differently the fourth time.

02 · What we built

One control plane, as many test nodes as you have

You describe a test once. Every machine in the bench runs its share of it, and every process reports on the same bus, so the client can draw the result while the run is still going.

What the user controls

One frame size or a mix of them in a chosen ratio, from 64 bytes up to 1518. Traffic that runs back to back or in bursts, with the inter-frame gap under your hand. A share of broadcast frames, to see how the switch copes with flooding. A PRNG seed and a payload type, so a run can be repeated exactly. Four presets cover the usual jobs: throughput, latency, frame loss rate and packet integrity.

How a packet proves itself

Every frame carries a two-byte stream id, an eight-byte sequence number, a timestamp the switch writes as the frame passes, and a four-byte CRC. That is the whole trick: with an id and a sequence number the verifier knows which stream a frame belongs to and whether any went missing, arrived twice or arrived out of order, and with the switch's own timestamp it can price the delay the switch added rather than the delay the network added.

03 · My part

The Admin Client: the control plane, the stream, and the client

Five of us built E‑Jam. The three I worked on sit together in the repository under one directory called Admin Client, and they are the route a number takes: a process on a test node counts something, and a chart on somebody else's desk has to show it.

Center Point is the Rust service on Actix Web that everything else talks to. Its REST API is the only way a test is created, started, stopped or inspected, and behind that API every stream, device and process moves through an explicit state machine rather than a pile of booleans. A stream is created, sent to the nodes, queued, started, and then finishes, stops or errors. Each of those edges is a named transition that can be refused. Being able to say "this stream cannot go from Queued to Finished" is what makes an unattended run trustworthy: a test that ends in a state nobody expected is a test whose result you cannot use.

Center Point also consumes the statistics topics, so it is the one place that knows what every node is seeing, and the one place the client has to ask.

The Kafka layer is how anything that happens on a node reaches the screen at all. Each node's System API produces its statistics onto topics. The messages are Avro, registered against a schema registry, so a producer and a consumer that disagree about the shape of a statistic fail at the registry instead of quietly halfway through a run. The stack itself comes up from one compose file (Zookeeper, the brokers, the registry, ksqlDB), so a new bench has a streaming layer before it has a test.

The Flutter client is the end of that path: it configures a test and charts the results as they arrive. The team moved it off Electron mid-project, which the project documentation records as the riskiest call we made. It was also the right one. The UI got fast enough to draw live data without falling behind it.

The stack, end to end

Five components, four languages, and which of them I worked on. Nobody wrote all of it.

Center Point my part
Rust · Actix Web. The control plane, and the only thing the client ever talks to. It is also the one process that has seen what every node has seen.
Streaming my part
Apache Kafka · Avro · schema registry. The bus every node's statistics travel on, typed at both ends. Zookeeper, the brokers, the registry and ksqlDB all come up from one compose file.
Admin client my part
Dart · Flutter. The cross-platform desktop client: configure a test, watch it draw. It replaced an Electron prototype halfway through the project.
System API
Java · Spring Boot. One per test node. It takes what Center Point sends, starts and stops the processes in Docker on that machine, and produces their statistics onto Kafka.
Generators, verifiers, gateway
C++. The processes that put frames on the wire and check what comes back, one container each, handing their statistics up through named pipes.
Switch under test
SNMP. Not ours: the device being measured, watched passively between runs.

GitHub's language breakdown puts about a tenth of the repository under C. There is no C component: the repository holds no hand-written C source, and that tenth is header and build files counted that way.
