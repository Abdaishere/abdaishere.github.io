The problem

Every client arrives with a business that already runs, and a list of what the software must do for it. Most of that list is covered by the standard platform. The engineering is in finding the part that is not, and building only that.

How I work it

I work directly with the client's team. First I map what they need onto standard features, then I put the rest into a data model and a delivery plan, and then I build it in Python and PostgreSQL: business logic, integrations, database fixes and performance work. More than a hundred enterprise client projects so far.

What lasted

When several clients in one industry asked for the same thing, I designed it once as a module. Five of those industry modules are now used by every client in their segment, which replaced custom code written one client at a time. I also review partner developers' code against Odoo's development standards, and train partner teams on the framework and on building modules.

Case 02 · 2026

PolyBall A rhythm game I designed, built and released alone.

My part
All of it: design, code, audio, release
Version
0.10.11 · the 19th tagged release
Status
Live on Google Play since 13 November 2026
Runs on
Android · browser · Windows, Mac, Linux

The problem

A rhythm game lives or dies on whether the tap lands on the beat, on a cheap Android phone as surely as on a desktop, in fifteen languages. With one person on the team, nothing can depend on remembering a step, so the plan was to automate every step before the first public release.

What I built

An audio engine that performs every note as you play it: sixteen instruments, up to twelve notes at once, colour mapped to chord degree, bass and arpeggio and lead laid down on a swung grid. No music files ship. Around it, continuous integration across six build targets, and gameplay bots that play twenty-four runs a pass and miss on purpose, so the economy numbers come out looking like a real player's. Opt-in telemetry re-derived the difficulty curve from real thumbs instead of my guesses. Fifteen locales, with Arabic laid out right to left and checked by tests rather than by eye.

Behind the game sits a leaderboard on Supabase (PostgreSQL) with a monthly cup. The server checks every score: score ceilings, a run code issued before each run, a name filter, block and report. It is eleven SQL migrations with automated tests.

Case 03 · 2023

E‑Jam A test bench for network switches, spread across many machines.

My part
The Admin Client: Center Point (Rust), the Flutter client, and the Kafka layer between them
When
January to August 2023
Context
Cairo University graduation project, five developers, with Siemens EDA engineers as mentors and product owner
Licence
MIT, public on GitHub

The problem

A switch is the box every packet in an office passes through, and a new one has to prove it can carry full traffic without dropping or delaying anything. The proof is a standard set of measurements at several frame sizes, each repeated many times. Run by hand it is long and repetitive, and the hand is the slow part.

What we built

E‑Jam spreads the work across as many machines as you give it. On each one, C++ generators fire traffic at the switch and verifiers check what comes back out, every process in its own container. Their statistics stream home over Apache Kafka, typed against a schema registry, and the client charts them while the test is still running.

My part

The repository calls it the Admin Client, and it is one path: something happens on a node and it has to reach a chart. I worked on all three pieces of it. Center Point, a Rust service on Actix Web, whose REST API drives every stream, device and process through explicit state machines. The Kafka layer that carries every node's statistics home, Avro-typed against a schema registry. And the Flutter client that configures a run and draws the results live.

How I work

Design it, plan it, ship it, check it

The tools change from job to job. This order does not.

  1. 01 · DesignStart from the need, not the tool. At Odoo every project begins with what the business has to do, mapped onto what already exists. Only the gap becomes a data model, and only the data model becomes code.
  2. 02 · PlanMake the wrong state impossible to reach. E‑Jam's control plane moves every stream, device and process through an explicit state machine, so a test cannot end somewhere nobody planned for. Before a full 3D print I print a small fit coupon first, for the same reason.
  3. 03 · ShipMake releasing boring. PolyBall went out as 19 tagged releases in under two months. One CI run builds six targets, and gameplay bots play 24 runs a pass, missing on purpose.
  4. 04 · CheckMeasure the thing itself. A check of mine once passed for three days while the browser build played no sound at all. It counted what was sent, not what arrived. I wrote down what that taught me.
